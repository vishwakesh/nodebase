# NODEBASE V2 foundation

## Scope of this branch

This branch adds the first multi-node vertical slice to the V1 workspace:

- A one-time enrollment token generated by an authenticated administrator, with a 15-minute lifetime and single-use enforcement.
- A node agent that initiates outbound HTTPS requests, exchanges the enrollment token for a unique node credential, stores the credential with owner-only file permissions, and reports heartbeat/host telemetry.
- Per-node token hashes (the token itself is returned only once at enrollment), credential revocation, drain/accept-workloads controls, and freshness-derived online/offline status.
- A mobile-responsive Hosting Nodes UI with live refresh and explicit unknown values when telemetry has not been reported.

This is not yet a complete remote workload scheduler. The agent currently reports its identity and host telemetry; it does **not** yet create bot containers on remote nodes or receive lifecycle commands. The existing single-host runner remains unchanged. Do not advertise multi-node bot deployment as complete until the remote command protocol, runner/runtime management, deployment tracking, and integration tests have shipped.

## Agent security model

1. Admin creates a temporary enrollment token. Only its SHA-256 digest is persisted.
2. Agent sends the token in a bearer header over HTTPS to `/api/agent/enroll`.
3. The API atomically consumes the token, creates a node record, and returns a distinct node credential once.
4. Agent saves its credential file using mode `0600` inside a directory with mode `0700`.
5. Agent sends heartbeats with that per-node credential. The API persists only its hash.
6. Admin can revoke the credential. Revoked credentials cannot send further heartbeats.
7. Node state is shown as offline after 90 seconds without a heartbeat; last-known metrics remain visible but are not represented as current status.

The agent refuses remote HTTP control planes. HTTP is allowed only for loopback development. The enrollment token is not saved after exchange. Back up the agent credential file securely; losing it requires revoking/re-enrolling the node.

## API additions

- `GET /api/nodes` — authenticated node inventory and freshness summary.
- `GET /api/nodes/:id` — authenticated node details.
- `POST /api/nodes/enrollment-tokens` — authenticated, CSRF-protected token issue; response includes one-time token and expiry.
- `POST /api/agent/enroll` — token-authenticated, one-time enrollment.
- `POST /api/agent/heartbeat` — per-node bearer-authenticated telemetry update.
- `POST /api/nodes/:id/drain` — administrator stops the node accepting new work (scheduler integration is pending).
- `POST /api/nodes/:id/accept-workloads` — administrator re-enables an online node.
- `DELETE /api/nodes/:id` — revokes its credential without claiming that its remote workloads were deleted.

Metrics not yet provided by an agent are represented as unknown (null/—), not fabricated zero values.

## Install an agent on another node

Build the agent image from this repository on a machine with Docker and registry access:

```bash
docker build -f agent/Dockerfile -t nodebase-agent:0.2.0 agent
```

On the panel, open **Hosting Nodes → Add node**, then copy the temporary token. On the remote node, first create `/srv/nodebase` as the intended storage filesystem/directory, then run the agent with the environment below. The directory is mounted read-only solely so the agent can query filesystem capacity; the enrollment token should be passed through a secret mechanism or shell environment, not committed to a file in Git:

```bash
docker run -d --name nodebase-agent \
  --restart unless-stopped \
  -e NODEBASE_CONTROL_PLANE_URL=https://panel.YOUR_DOMAIN \
  -e NODEBASE_NODE_NAME='worker-01' \
  -e NODEBASE_REGION='region-label' \
  -e NODEBASE_ENROLLMENT_TOKEN='PASTE_ONE_TIME_TOKEN' \
  -e NODEBASE_AGENT_RUNTIMES='python,node' \
  -e NODEBASE_AGENT_STORAGE_PATH=/host-data \
  -v nodebase-agent-credentials:/var/lib/nodebase-agent \
  -v /srv/nodebase:/host-data:ro \
  nodebase-agent:0.2.0
```

Prefer a protected secret injection mechanism rather than storing the one-time token in shell history. After enrollment the token is exchanged and the resulting node credential is stored in the named volume. The agent does not expose a management port and only needs outbound HTTPS access to the control plane.

The currently advertised runtime list is an agent capability declaration, not proof that a remote bot lifecycle runtime has been installed or that remote workload scheduling is ready. The remote deployment executor is a planned next phase.

## Database decision

V1 uses SQLite and the node inventory migration remains compatible with that existing deployment. This minimizes migration risk for the first vertical slice. Before operating a large multi-admin/high-write deployment, migrate the control-plane database to PostgreSQL with an explicit tested data migration; this branch does not claim that migration is complete. Keep the current data directory and V1 deployment untouched while testing.
